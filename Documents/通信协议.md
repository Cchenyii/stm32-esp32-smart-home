# 通信协议 V1

## STM32 与 ESP32

UART 115200 baud、8N1、无硬件流控。帧格式为 `AA 55 | version:u8 | type:u8 | seq:u16 | len:u16 | payload | crc:u16`。帧头是固定顺序的两个字节。其余多字节值为小端。版本为 1，最大负载 64 字节，最大整帧 74 字节。CRC16/CCITT-FALSE 覆盖 version 至 payload 的所有字节，初值 `0xFFFF`，多项式 `0x1021`，无反转、无最终异或，`123456789` 的结果为 `0x29B1`。

负载按列出顺序逐字节写入，C 结构体的内存布局不参与编码。

- `01` 传感器，16 B。`温度 0.1°C:s16`、`湿度 0.1%:u16`、`距离 mm:u16`、`标记:u16`、`采样时运行毫秒:u32`、`STM32 样本丢弃计数:u32`。
- `02` 状态，36 B。8 个 `u32` 依次为运行毫秒、采集周期毫秒、CRC 错误、头部和超时错误、UART 错误、OLED 错误、丢弃样本、RCC 复位标记。再接任务最小栈余量 `u16`（字）、板级配置状态 `u8`（1 校验通过，2 配置不合法）、看门狗状态 `u8`（0 未启动，1 喂狗，2 关键任务超时）。
- `03` 心跳，4 B。发送方运行毫秒 `u32`。两端约每 2 s 发一次，8 s 未收到对端有效消息判定串口链路不在线。
- `04` 命令，9 B。`rid:u32`、`op:u8`、`value:u32`。`op=1` 设置采样周期毫秒，`op=2` 查询状态，此时 value 为 0。
- `05` 回执，10 B。`rid:u32`、`op:u8`、`result:u8`、`当前采样周期毫秒:u32`。查询状态回执之后发一帧状态。
- `06` 传感器故障变更，6 B。`故障位:u16`、`采样时运行毫秒:u32`。故障位清零代表恢复。

传感器位掩码按 1、2、4、8、16、32、64、128 表示温湿度有效、距离有效、DHT 等待超时、DHT 数据或脉宽无效、Echo 超时、Echo 范围无效、DHT 未配置、测距未配置。无效数据在 TCP 中为 `null`，OLED 显示 `NA`。

接收端处理分片和连续帧。候选帧长度越界或 CRC 失败后，从剩余数据中重新寻找帧头。残帧超过 100 ms 回收。串口缓冲溢出或底层接收错误后清缓冲并继续接收。序号按发送方递增并循环，只用于观察顺序。V1 没有数据帧重传。

## ESP32 与 PC

PC 为 TCP 服务端。每条消息是一个 UTF-8 JSON 对象，以 LF 结束，连 LF 最大 768 B。所有消息带 `v:1`，设备上行带 `device_id`。设备编号由 1–31 个字母、数字、下划线或连字符组成。

- **ESP32 → PC**。首包为 `hello`，带 `simulated`。后续消息类型为 `ping`、`sensor`、`status`、`error` 和 `response`。温度为 °C，湿度为百分比，距离为 cm。
- **PC → ESP32**。收到 `ping` 回复 `pong`。命令类型为 `command`，带非零 `rid` 和 `op`。`op=set_period` 需要 `period_ms`。`op=get_status` 查询设备状态。ESP32 每个连接同时转发一条待回执命令。
- **结果码**。0 成功，1 参数无效，2 命令不支持，3 忙，4 UART 不可用，5 等待 STM32 回执超时。PC 只接受编号和操作都匹配的回执。超时表示执行结果未知，可在设备恢复时查询状态。
- **断线**。ESP32 每 3 s 发 `ping`，12 s 未收到 `pong` 则断开并退避重连。PC 12 s 无有效消息即离线。网络离线时 ESP32 保留最新一份样本和状态，恢复后补发队列中已有的最新值。

```json
{"v":1,"type":"command","rid":42,"op":"set_period","period_ms":5000}
{"v":1,"type":"response","device_id":"edge-01","rid":42,"op":"set_period","result":0,"period_ms":5000}
```

## 智能家居配置

STM32 的 `EDGE_HOME_PROFILE` 与 ESP32 的 `EDGE_HOME_MQTT` 组成一对。它们沿用 V1 的帧头、CRC、长度边界和 115200 8N1。智能家居消息编号为十进制。负载使用小端，字段顺序如下。

- **7 会话同步，4 B**。非零 `session:u32` 由 ESP32 生成。STM32 的状态帧回显会话。同步只建立命令会话，不改变当前模式或输出。会话建立后，ESP32 每约 1 s 用 3 型帧发送 4 字节心跳。
- **8 状态，26 B**。两个 `u32` 为 `session`、`uptime_ms`。再依次写 `temperature_tenths:s16`、`humidity_tenths:u16`、`light_raw:u16`、`light_level:u16`、`fan_on_tenths:u16`、`close_level:u16`、`dht_flags:u16`。末尾四个 `u8` 为 `flags`、`curtain`、`curtain_target`、`source`。STM32 每约 500 ms 发一份快照，处理命令后也会主动上报。
- **9 命令，11 B**。`session:u32`、`id:u32`、`op:u8`、`value:u16`。帧序号取 `id` 的低 16 位。一个会话内 ID 从非零开始递增。
- **10 回执，10 B**。`session:u32`、`id:u32`、`op:u8`、`result:u8`。回执帧序号与命令一致。执行器命令的成功回执在控制任务更新 GPIO 或 PWM 后生成。

`flags` 的 1、2、4、8 分别表示温湿度有效、光照有效、手动模式、风扇开启指令。`dht_flags` 沿用温湿度有效及 DHT 故障位。`light_raw` 是 ADC 原始读数，`light_level` 为按模块方向统一到越亮越大后的 0–4095 数值。窗帘值 0、1、2 分别是待命、开、关，`curtain_target` 可表示等待动作间隔的目标。`source` 的 0、1、2 分别表示默认设置、本地按键、最近接受的远程设置。

远程操作均写入绝对目标。1 设置模式（0 自动、1 手动），2 设置风扇（0 关、1 开），3 设置窗帘（1 开、2 关），4 设置风扇开启阈值（100–600，单位 0.1°C，步长 10），5 设置关帘阈值（600–4000，步长 100）。风扇回差为 2°C，窗帘回差为 500 个计数。直接操作风扇和窗帘需要手动模式。本地按键持续按住、操作后约 1.2 s 内、或停留在本地菜单及其子页时，本地优先。

STM32 结果码为 0 已更新、1 参数非法、2 不支持、3 忙、4 需要手动模式、5 本地优先、6 会话或命令已过期、7 窗帘目标已接受并等待动作间隔。ESP32 的 8 表示 STM32 不可用，9 表示等待回执超时。超时时执行结果未知，以恢复后的状态为准。一个会话中重复的最新命令返回缓存结果，较旧的 ID 被拒绝。ESP32 仅允许一条待回执命令，使用同一帧序号和 ID 最多发送三次。连线或 MQTT 会话恢复后换用新令牌，并等待 STM32 返回当前状态再接收控制。

### MQTT 与网页

主题前缀为 `smarthome/<device_id>/`。Broker 用账号及主题 ACL 区分网关和网页。状态和回执由网关上行，网页只向命令主题发请求。

- `state` 是非保留的实时 JSON，字段与 8 型对应，额外带 `last_id`、`uart_errors`、`uart_crc_errors`。网页在约 3 s 没有新状态时清除旧读数并关闭控制入口。
- `command` 是非保留的 JSON。网页以 QoS 0 发布，等待 STM32 回执后显示结果。网关订阅 QoS 1，可接收受 ACL 授权的 QoS 1 客户端。旧会话 ID 和保留命令均不进入控制任务。
- `ack` 使用 QoS 1，非保留。网页按会话、ID、操作同时匹配。`confirmed` 表示应答源自 STM32，返回码仍可能是拒绝或延后。
- `availability` 是保留的 `online` 或 `offline`。ESP32 的遗嘱为 `offline`。网页还检查实时状态是否有效。

```json
{"session":123456,"id":42,"op":3,"value":2}
{"session":123456,"id":42,"op":3,"result":7,"confirmed":true}
```

## ThingsBoard Cloud

云端模式是 ESP32 的另一种 MQTT 配置，沿用上述 STM32 串口帧、状态与结果码。设备通过 TLS 连接 ThingsBoard，完成网络校时、验证服务器证书及主机名后使用设备 token 登录。

- **遥测**发布到 `v1/devices/me/telemetry`。第一次收到当前会话的 STM32 状态后即尝试上报，之后每 30 s 上报一次，模式、执行器、阈值和传感器有效位的变化可触发提前上报，限频 1 s。无效传感器用布尔有效位标识，省略对应数值。UART 掉线时，如果 MQTT 仍在线则发布 `{"uart_online":false}`。整个网关离线时，手机面板靠即时 RPC 探测连接状态。
- **实时读取**为 `getHome` 双向 RPC，`params` 为空对象。仅返回当前有效的 STM32 快照，附上 `session` 和 `last_id`。没有当前快照时返回 `{"uart_online":false}`。
- **控制**为 `setHome` 双向 RPC。参数为 `{session,id,op,value}`，其中会话来自 `getHome`，ID 大于本页面已经发送的 ID 和设备返回的最新 ID。该会话在 MQTT 重连、Wi-Fi 丢失、UART 重连后重新建立。保留的 MQTT 命令与过期会话不进入 STM32。
- **回执**发到 `v1/devices/me/rpc/response/<request_id>`，`request_id` 来自 `v1/devices/me/rpc/request/<request_id>`。控制结果仍为 `{session,id,op,result,confirmed}`。手机端校验三项关联字段，再据 STM32 返回码显示结果。超时或不匹配时读取新状态，避免自动重发。

小部件以约 7 s 的间隔获取当前快照，指令完成后也立即刷新。平台配置采用即时 RPC。配置、部署和实体绑定见 [ThingsBoard Cloud 接入](上板配置与验收.md#thingsboard-cloud-接入)。
